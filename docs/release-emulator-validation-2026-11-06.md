## Confirmed findings

### New-note table insertion fails in the actual Capture flow

1. Open Note from the radial FAB and continue into the full editor.
2. Focus the body; scroll the keyboard accessory bar to Insert table.
3. Open the table dialog and confirm its default 3 × 3 dimensions.
4. The dialog closes but the source is unchanged. The accessory scroll position
   resets. A fresh follow-up UI capture still has no inserted table.

Evidence: `15-table-dialog.png`, `17-table-created.png`,
`20-after-table-idle.png`, associated XML and `events.jsonl`.
The earlier focused test activity kept its table controls mounted and passed;
that did not establish correctness for Capture's keyboard-dependent lifecycle.
A later saved-note native-editor check successfully inserted a 3 × 3 table,
added one body row and added a fourth column. Add row hid the keyboard/toolbar;
the next tool required restoring IME focus through the title. Thus the saved
source transformations passed, but the interaction flow did not. The temporary
table edits were left unsaved and Cancel returned to the reader. Evidence:
screenshots 325–340 and `saved_editor_*` events.

The formatting command currently owns a composition coroutine scope in
`CobaltSelectionMenus.kt`; toolbar disposal during a dialog is a candidate to
investigate, not yet a demonstrated cause.

### Saved-note native keyboard invocation is unreliable on this emulator

Tapping the saved note body positioned the cursor but left
`dumpsys input_method` at `mInputShown=false`. Repeating the tap did not open it.
Focusing the title first and then the body kept the keyboard visible. An Undo
accessory action later closed it. Hardware input still edited the source.

Evidence: `32-native-keyboard.png`, `33-native-second-tap.png`,
`34-native-typing.png`, `36-title-keyboard.png`, `37-native-with-ime.png`.
Root cause and reproduction on other Android versions are unverified.

## Dataset and measurement limits

Generated sources cover one line, 1 KB, 100,000 ASCII characters, 1k/3k/5k/10k
links, 50,000 plain lines, 2 MB plain, 5 MB plain/link-heavy, 50 MB plain/link-heavy,
54 MB and 55 MB. A 56 MB source is expected to be refused. Extra plain notes fill
the synthetic dataset to 1,000,000,000 bytes. MB/GB here are decimal source bytes.

The runner confirms the review title and expected Home count after every Save.
It records source sizes/hashes. The release app is non-debuggable and this AVD
cannot enable root (`adbd cannot run as root in production builds`), so private
Room rows/body hashes cannot be inspected by the debug-only old stress runner.
UI-confirmed saves must not be described as private-file hash verification.

UI Automator acquisition adds seconds to import observations. Those durations
are upper-bound end-to-end observations, not precise copy/parse time or proof of
sub-second opening. PSS snapshots are not peak Java heap. Gfxinfo measurements
will be labeled by their actual screen and workload.

The import matrix completed; additional runtime results follow.

## 54 MB editing, Undo/Redo and saved integrity

The disk-backed editor exposed a bounded 16,384-character accessibility buffer.
Ten separate hardware text commands inserted `0123456789` at the document start.
Ten Ctrl+Z commands returned the prefix to the original text. Ten rapid Ctrl+Y
commands restored only `012345678`; a fresh capture after settling was unchanged.
One additional Ctrl+Y restored the final `9`. This is a failed rapid-Redo test:
a command was dropped or ignored. The disk editor currently rejects actions
while `loading`/`blocked` in `DiskMarkdownView.action`; that is a candidate cause,
not a proven trace.

After restoring all ten characters, Update Archive completed and the reader
showed the correct prefix. The first export probe ran while the button still
said Saving and was corrected to wait; this is an automation timing error, not
an additional app defect. The completed export had 54,000,010 body bytes and
matched a generated reference of the original 54 MB body prefixed by the ten
characters. Sampled editor PSS was 84,136 KiB (about 82 MiB), not a measured peak.

Evidence: `83-54mb-ten-edits.png` through `87-54mb-redo-extra.png`,
`editor-54mb-meminfo.txt`, `54mb_edited_export_integrity` event.

## Version storage, Trash, restore and permanent deletion

Five total saves of the same 54 MB note retained 108 MB of physical history in
the sampled Storage report, rather than five complete 54 MB history copies.
The history browser showed five 54 MB logical versions; its per-version size
labels do not distinguish logical body size from physical delta storage.
Source uses full anchors plus bounded one-level deltas and optional background
compaction. This does not justify promising “only tiny deltas” or immediate
compaction under every workload.

With Trash enabled (default), deletion removed the item from the active list
(32 → 31), grouped its body and history under Trash (162 MB), and showed
30 days remaining. Restore returned the count to 32 and preserved the exact
`DCBA0123456789Plain...` prefix from the five save cycles. Deleting again and
confirming Delete forever emptied Trash. Storage then reported approximately
0.95 GB of notes/media, 1.1 kB history, 0 B Trash, 221 B unlinked, 49 B recovery
and 601 kB cache. Thus the note's body/history were reclaimed in this case.
The test permanently removed only its own synthetic large note.

The ordinary reader Delete Archive dialog incorrectly said “This action cannot
be undone” while Trash was enabled and restoration worked. This is a confirmed
misleading UX message. The permanent-deletion dialog correctly warned that it
removes the item, versions and recovery files. Actual 30-day automatic expiry
was not simulated.

Evidence: `150-storage-five-saves.png`, `153-history-versions.png`,
`157-delete-confirm.png`, `162-trash-large.png`, `168-restored-reader.png`,
`176-delete-forever-confirm.png`, `179-storage-after-purge-refresh.png`.

## Later APK upgrade and confirmed release-only WorkManager failure

A later prebuilt APK was copied to `upgrade-release.apk` before installation:
SHA-256 `12ace7cede0db022000d985d6dffa50948ab36a21d4a8a8a32d91c8014e6ee2a`.
Installing with `adb install -r` preserved the library and filters; all 38 items
at that stage remained present. A later continuation displayed 39 items,
including a small Quick Note test item. The full performance/import matrix
above was not repeated on this newer artifact.

The newer APK's R8 marker matched mapping ID
`e7a7d4bf558e42bef6a7a35885b98b38001da82bab528d16651b7239c49e7e79`;
its matching mapping is archived as `upgrade-mapping.txt.gz`.
New-note Capture table insertion was retested and still failed on this APK.

Release logs showed `NoSuchMethodException` for
`androidx.work.OverwritingInputMerger.<init>[]`. APK inspection confirmed that
both built-in InputMerger classes lacked their public zero-argument constructor.
The same structural check passed for both classes in the debug APK. This can
fail one-time work before its Worker runs. A periodic safety worker eventually
fetched the saved link metadata, which does not establish that the one-time
queue worked. The connectivity-toggle probe did not strictly verify offline
isolation and must not be treated as a rigorous offline-network test.

Commit `650c2cf` adds a narrowly scoped InputMerger constructor keep rule and
`tools/check-release-workmanager.sh`. Negative control: existing release fails
both constructors. Positive control: existing debug passes both. The fixed
release has **not** been verified: the one-worker, 1536 MiB heap, offline release
build failed at Kotlin compilation on unrelated in-progress ImageShare sources
referencing a missing `description` property. No R8 task completed. Those
concurrent edits were not changed or reverted.

A detached validation checkout of committed code was prepared under
`/tmp/cobalt-r8-validation`. Automatic permission approval for its bounded
release build timed out on both the initial request and the single retry; the
build did not start. This is an approval timeout, not a test pass or a judgment
that the build is unsafe. No memory cap was raised.

Evidence: `upgrade-artifact.json`, `upgrade-work-details.txt`, archived APK and
mapping; `/tmp/cobalt-release-merger-check.log`,
`/tmp/cobalt-debug-merger-control.log`,
`/tmp/cobalt-release-keep-validation.log`.

## Coverage limits and release decision

**Release approval is withheld.** Confirmed unresolved issues include Capture
table insertion, rapid Redo dropping a command, unreliable saved-editor IME
invocation on this emulator, misleading Trash deletion wording, and scrolling
far outside the performance budget. The WorkManager keep-rule fix still needs
an integrated R8 build and runtime retest.

Not completed: API 29/31/34/36 or low-RAM matrix, physical-device measurements,
Macrobenchmark jank/typing latency, peak heap and sustained CPU sampling,
split-screen, exhaustive IME composition/selection and all Markdown toolbar
operations, ten Undo/Redo steps on every note, full historical database migration
fault injection, 30-day Trash expiry, cache clearing/compaction (the sampled UI
reported no safe cache available), and authenticated Trakt/TMDB/Gemini flows.
No integration credentials were supplied or accessed. Tests do not certify all
codecs, all malformed files, all storage failures, or all URL providers.

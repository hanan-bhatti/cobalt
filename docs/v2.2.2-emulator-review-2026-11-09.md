# GitHub v2.2.2 emulator baseline

Review date: 9 November 2026. This report separates observed Android behavior from source changes and untested features. It is not a claim that every feature or supported device passed.

## Installed baseline

- Downloaded `cobalt-foss-v2.2.2.apk` from the actual [GitHub release](https://github.com/hanan-bhatti/cobalt/releases/tag/v2.2.2), published 27 October 2026. This is the published binary, not a rebuild of the tag.
- APK: **5,740,067 bytes**; SHA-256 `4929519a546e53ca051da3087b185b27412204a2fbf2ee2099c29ce1e9a8776d`.
- Uninstalled the previous production package and installed the baseline. Android reported `com.hanan_bhatti.cobalt`, version **2.2.2**, code **18**, target/min SDK **37/24**.
- Device: `emulator-5554`, Google `sdk_gphone16k_x86_64`, Android 17/API 37, 16 KiB pages, display 1344 × 2992. Hardware keyboard input was enabled; this does not validate soft-keyboard bugs on physical phones.
- The separate debug package was not cleared. Private original-data backups and raw test evidence are outside the repository in `~/.local/state/cobalt-review-2026-11-09/`.
- Usable Gemini/TMDB key extraction **failed**. The original-data backup includes encrypted preferences, but encrypted preferences alone are not a portable key backup. The clean baseline has no configured integration keys. No successful Gemini, TMDB or authenticated Trakt test is claimed.

## Saved-note fixtures and integrity

Four text records were saved: a mixed Markdown note, two 100k-character records (one was subsequently edited), and a 400k-character note. The repeated 100k title arose during failed/retained share-launch attempts; it is not evidence that a duplicate-prevention rule was tested.

- Small fixture contained headings, checked/unchecked tasks, a Markdown table, fenced Python, Urdu, emoji and accented text. The reader exposed the expected content.
- A synthetic ASCII **100,000-character** fixture contained `START 100000` and `END fixture marker`. After Save and opening the reader, Copy recovered exactly **100,000 characters**, including both markers.
- A later edit recovered **100,015 characters** after closing/reopening, including `REVIEW_EDIT_MARKER`. The additional keystrokes did not constitute a successfully established 200k paste.
- A synthetic **400,000-character** fixture was placed on the clipboard by a separate emulator-only helper and pasted with Cobalt's visible **Paste from clipboard** control. Save added `Review-400k` with `START 400000` to Home; its reader eventually opened.
- Full Copy recovery of the large note returned **399,995 characters** with both markers. It matched an independently generated fixture after trimming. The five missing characters were the fixture's five trailing spaces: baseline Capture explicitly calls `.trim()` when reading the clipboard. This is clipboard normalization, not a verified byte-preserving import.
- Android accessibility text is bounded. A hierarchy exposing only a prefix does **not** establish body truncation or full integrity. Full large-note integrity was established by the independent clipboard round trip above, not by the hierarchy.
- 5–55 MB files, 1 GB libraries, thousands of items, high-entropy bodies, disk-full and hardware power loss were **not** validated against this published APK. These need separate tests; source support or a different build's report is not a substitute.

## Reproduced behavior and failures

### Stale reader after saving an edit

1. Open a saved note and choose Edit Item.
2. Change its text and Update Archive.
3. The already-open reader continues to show/copy the previous content.
4. Close the reader, reopen the same saved note and Copy again.

The first copy remained the original 100,000 characters with no edit marker; the reopened copy contained the saved marker and had 100,015 characters. This reproduces stale reader state, rather than proving a lost edit. Current source changes intended to address this are tracked in the comparison; current-build verification is separate.

### Large text share launch failure

A 200k-character ACTION_SEND attempt through the fixture helper did not establish a saved 200k record. Android exit records at 17:03 recorded the old Cobalt process terminated by SIGKILL and a subsequent process killed for **ACTIVITY LAUNCH FAILURE / “2nd-crash”**. ActivityTaskManager reported failed lifecycle dispatch during launch. This is an Android/Binder launch-path failure observed during large sharing, not a demonstrated editor OOM or a lost saved database.

Earlier failed helper navigation and stale accessibility dumps were excluded from successful tests. Normal launcher startup recovered the saved library. Raw logs are retained privately for exact attribution.

### Large reader latency

Opening the 400k note produced repeated “null root node” accessibility responses before the reader hierarchy settled. The reader eventually opened. The available Android last-ANR report said **no ANR since boot**. No precise user-perceived open latency or peak RAM claim is made from polling delays.

### Survey accuracy

The survey offers “Private Vault & Biometrics” as a favorite feature while offering backup/restore and a companion app as requests. A biometric lock was not found/verified. Treat this as misleading feature copy pending the user's separate survey task. Do not call encrypted API credentials encrypted notes.

## Final Side Dock probe

After granting overlay permission and enabling the actual switch, Android reported `CobaltSideDockService`, `isForeground=true`, notification 9283 and foreground type `0x40000000` (specialUse). No new Cobalt crash was observed. Handle Position & Geometry and Motion & Expand Physics pages opened and returned. The switch was disabled and the temporary overlay app-op returned to default afterward. This does not test API 29–33 foreground-service compatibility, Dock note capture, region OCR, or background restart reliability.
